# Appendix B — 15 Business-Semantic Checks (v2.0.2)

This is a **manual/model-assisted review specification**, not implemented automatic scoring or a claim that lint checks business meaning. Use it for generation, review, optimization and acceptance. The local delivery script may prepare a checklist with `pending` status; creation of that checklist is not a pass. A reviewer must record evidence and disposition for each item.

Use the exact IDs from `scripts/prepare_delivery.py` `REVIEW_CHECKS` below. Record `id | status (passed/failed/pending/not_applicable) | evidence | reasoning | action/owner` in the review artifact; explain every not_applicable result. Unknown/TBC semantics remain `pending`, not `passed`. Upload is blocked by unresolved required semantics or pending review; do not mark all checks passed from a machine-lint result. Structural tests, semantic review and remote acceptance are separate gates.

| ID | Check | Required evidence and acceptance |
|---|---|---|
| preset_fields | Preset fields and SDK guarantees | Do not duplicate system/preset fields in custom tables or invent SDK auto-collection support. Confirm platform and SDK capabilities; identity system rows are distinct from custom event/user properties. |
| metric_coverage | Metric-to-event mapping | Each requested metric has subject, numerator/denominator, time window, dedup unit, event/property path and real data source. Do not claim unavailable click/revenue data is analyzable. |
| identity | Identity applicability | Declare account/no-account, visitor ID, role/account mapping and binding timing. For no-account E1, empty account_id alone is not High when valid distinct_id exists. Both IDs absent is a separate defect. |
| trigger_semantics | Business fact and granularity | One event represents one implementable fact; batch/entity granularity is explicit. Avoid mechanical show/click/result expansion or duplicate facts for different reporting sides. |
| correlation | Correlation and lifecycle | Start/process/result share a stable correlation key with generator, keep/reset and retry rules. Cover exit/cancel/timeout where relevant. Paired events need not have identical object groups. |
| ads_chain | Failure and IAA closure (E1) | Explicitly include ad_fail with failure trigger/reason where the IAA case requires it, and cover impression/completion/reward. Revenue without a confirmed provider is labelled “requires ad-platform callback / TBC” (translate explanation to user language); no invented callback or amount. |
| attribution | First/current attribution (E2) | first_media_source and first_campaign represent first confirmed attribution via user_setOnce. media_source/campaign are per-event snapshots; current_* may update via user_set. They are not interchangeable, nor global common properties by default. Confirm MMP/platform source. |
| property_registry | Property registry, units, enums and nulls | Same meaning reuses name/display/type/unit/enum within event+common or user domain; different meanings get different names. Common properties apply to nearly all events with stable trigger-time values. Amount/currency, duration/timezone, ID semantics and missing-data rules are explicit; unknown facts are TBC, not invented enums. Cross-domain consistency is semantic review, not global lint enforcement. |
| object_structure | Composite modeling | Single object, scalar list and variable entity collection are distinct. Same parent name means genuinely matching child schema; different business structures use different parents. No meaningless filler fields or concatenated pseudo-structures. |
| privacy | Personal-data need and minimization | Each personal-data field has a stated business need, lawful/authorized collection basis and minimization review. Avoid exposing raw identifiers in diagnostic examples, unnecessary sensitive fields, secrets or credentials. |
| user_updates | User-property update semantics | Confirm first/current/cumulative/list meaning. Only user_set, user_setOnce, user_add, user_append are assumed plan-import operations. A legacy timing phrase is not an alias for an update method without confirmation. |
| reporting_authority | Reporting authority and dedup | Confirm actual client/server availability, one authoritative business fact, retry behavior and dedup window/key. Dual-side reporting must not double count; plan design is not evidence of real runtime dedup. |
| existing_plan_diff | Existing baseline, changes and conflicts | Disclose additions/renames/removals, their compatibility impact and exact existing-target conflicts using a verified baseline. Keep original files unchanged. Resolve conflicts explicitly; generation or one-click upload never authorizes implicit deletion/overwrite. Bind review to the actual target and baseline fingerprint. |
| language_and_counts | Language, actual counts and source parity | Opening/route/questions/body/acceptance and authored business descriptions follow user language. Fixed Chinese sheet/header/type labels remain Chinese, not an all-English template. Compute actual distinct nonempty event_name counts from canonical JSON and workbook event blocks, not property rows/styled dimensions. Online view, Excel, metric mapping, diff counts and report agree; do not repeat the historical 28-as-22 mistake. |
| unknowns_and_delivery | Scope, unknowns and reviewable delivery | Confirm category/core loop/modules/revenue model; label template borrowing/inference vs confirmed facts. Idle Card uses confirmed Idle + Card composition, not fabricated cache content. Show the plan in-session first and expose Notes/Timezone, TBC and diffs. Then offer direct structured sync or local Excel; do not create an unrequested workbook. Excel deliveries require complete 11 sheets, seven unchanged instructions, official repaired headers and first/final lint. Sync deliveries require source/payload parity and dry-run evidence, with no Excel intermediate. Required unknowns remain pending. Validated-upload owns the later destination/version/scope confirmation, with no implicit delete/overwrite or fabricated UI button; remote success needs real execution/read-back. |

## Evidence Boundaries

- A local unit-test pass proves only the exercised local contracts. It does not prove these 15 semantic checks, cloud upload, UI behavior, company deployment, or SDK runtime correctness.
- D1 first-call routing, seven E1–E7 content cases, C5 non-owner deployment permissions and D4 real dual-side dedup are distinct evidence scopes; see [evaluation cases](eval-cases.md).
- `Not run`, `TBC`, `blocked by missing input`, and `dry-run only` are not `pass`. Keep the historical isolated v2.0 record separate from v2.0.1 results.
- [Validated Upload](workflows/validated-upload.md) owns remote prerequisites and confirmation. Lack of CLI/auth or permission to perform remote work must be disclosed, not bypassed by guessed APIs.
