| Below we use a basic scenario to explain how to design the user ID system when tracking in the TA system. For more complex scenarios, feel free to contact ThinkingData's service staff. |  |  |  |  |
| Assume the current project has the following ID system: role ID, account ID, device-related IDs (including device ID or some third-party IDs based on the device, such as adjust_id) |  |  |  |  |
| In the TA system, `#account_id` is the primary standard to identify a single user; i.e., different `#account_id`s must correspond to different `#user_id`s. `#user_id` is the basis for user identification in the TA system. |  |  |  |  |
| In general, we recommend using the smallest, indivisible business ID as `#account_id`; in the above scenario, that is the role ID. Use a device-related ID as `#distinct_id`, such as the device ID, the guest ID generated by the ThinkingData client-side SDK, or a custom guest ID. |  |  |  |  |
| Other IDs are recommended to be recorded as common event properties (if the ID has a many-to-many relationship with the role, such as device ID) or as user properties. Based on the above logic, we recommend tracking as follows (below, the guest ID is the default guest ID from the ThinkingData client-side SDK; in practice this can be set as a custom one). |  |  |  |  |
| #account_id | #distinct_id | Account ID (custom property) | Device ID (custom property) | Other IDs (custom property) |
| Role ID | Guest ID | Account ID | Device ID | Platform ID, adjust_id, etc. |
