## 1. Template Excel Structure

### Four Data Sheets Within the Complete 11-sheet Workbook

Use the repaired v2.0.1 Chinese template with seven unchanged instruction sheets. English table descriptions below explain semantics only; they are not sheet/header strings to write. This version deliberately upgrades the old eight-column event data layout to the official nine-column import schema. Conversation and business prose follow the user language; Chinese template labels stay unchanged. See `export-schema.md` for canonical JSON and finalizer commands.

#### Sheet 1: #用户ID体系


| Column | Meaning                         |
| ------ | ------------------------------- |
| A: Product Type | No account / Single account / Single account, multiple roles |
| B: Property Name | `#account_id`, `#distinct_id` |
| C: Property Display Name | Display name |
| D: Property Description | System property description |
| E: Assignment | How it is assigned |

Remarks are preserved in the existing assignment/description cells; there is no new remarks column.


**User ID scheme selection rules**:

- No account system: tool-type Apps that do not require login; `#account_id` is empty, and `#distinct_id` is auto-generated by the SDK or is a device-related ID
- Single account system: Apps with a login/registration flow; `#account_id` = registered account ID, and `#distinct_id` is auto-generated by the SDK or is a device-related ID
- Single account, multiple roles (games): `#account_id` = role ID, and the account ID is used as a custom property. Use the smallest indivisible business ID as `#account_id`; `#distinct_id` is auto-generated by the SDK or is a device-related ID
- Fill when available, leave empty otherwise: when there is no role ID at device activation, leave `#account_id` empty

## 4. Category-Specific Event Modules

**General module replacement rules**
- Adapt the naming of personalized characters accordingly. For example, `hero_*` should be replaced with `ship_*` in a warship theme, and `monster_*` in a monster theme; this rule mainly applies to the progression module, the gacha result information in the gacha module, and the lineup information in the battle module.
- For the battle module, personalize naming based on the actual module name to distinguish different battle modules. For example, main-line battles use `stage_battle_*`, and resource-related stage battles use `resource_battle_*`. Except for main-line content, prefer translating module names according to the game's in-game terminology.
- Paired events share a stable correlation key and relevant context, not necessarily every property or an identical object-group schema. Result-specific rewards/damage and start-specific lineup snapshots stay where business semantics require. Reuse a parent name only for genuinely identical meaning/schema; otherwise use different names, never filler fields.

## 5. User Property Generation

> Provided for SKILL.md step 6 lookup. Based on the already-generated event data, extract user properties according to the rules below, from the generated event data and the user-provided functional modules.
> User properties are the foundation of the user profile and should cover the user's device info, account info, asset status, progress status, key time points, and cumulative behavior as completely as possible.
> The categories and samples below apply to all kinds of games and App products, and may be added or removed per the actual business.
> Object-group generation rules follow Section 6.

### 5A. Device & Account Basic Properties

First-touch `first_media_source` / `first_campaign` use user_setOnce. Per-event `media_source` / `campaign` and latest `current_*` user_set snapshots are separate semantics; do not substitute them or promote attribution globally. SDK preset device properties are not automatically custom user properties: confirm actual need/source.

**Update method: user_setOnce (set once, unchanged afterwards)**

| User Property Meaning | User Property Name | Type | Description |
| --- | --- | --- | --- |
| Device ID | device_id | Text | Unique device identifier; recorded at first activation |

| OS Version | os_version | Text | e.g. iOS 17.4 / Android 14, etc. |
| Client Version | client_version | Text | Game/App client version at user registration |

## 5. Property Type Rules (TE System 7 Types)

| Type | JSON Type | Value Sample | Applicable Scenarios |
| --- | --- | --- | --- |
| Text | String | `"ABC"`, `"Shanghai"` | Names, channels, IDs (when not purely numeric). Default limit 2KB |
| Number | Number | `123`, `1.23` | Amounts, levels, durations, purely numeric IDs (when ordering matters). Range -9E15 to 9E15, up to 3 decimal places |
| Boolean | Boolean | `true`, `false` | Is first, is paid, is bot |
| Datetime | String | `"2024-01-01 00:00:00"` | Registration time, first-payment time. Format `yyyy-MM-dd HH:mm:ss` or `yyyy-MM-dd HH:mm:ss.SSS` |
| List | Array | `["a","1","true"]` | Tag lists, skill lists, equipment lists. Elements are uniformly converted to strings |
| Object | Object | `{"item_name":"Shard","item_num":5}` | A single composite entity. See "Object Group Rules" |
| Object Group | Array(Object) | `[{"id":"001","num":5},{"id":"002","num":2}]` | Multiple composite entities of the same kind. See "Object Group Rules" |


**ID Property Type Selection Rules**:

- When ID ordering is positively correlated with numeric magnitude (e.g. stage ID `1,2,3...`) -> Number
- When the ID contains non-numeric characters or is unordered -> Text
- When unsure -> Text (safer; the type cannot be changed once determined)

**The type is immutable once first ingested**: the TE system property type is determined by the first ingested record and cannot be changed afterwards. The tracking plan must strictly label types.

## 6. Object Group Rules (TE Platform Constraints)

### 6.1 Definition

An Object Group = an array composed of multiple objects; the data format is `Array(Row)`.
Equivalent to an **n-row x m-column table** (n = number of array elements, m = number of key-value pairs per object).

```
Object:     {card_type:"Warrior", card_name:"Zhang Fei", card_id:123}
Object Group: [{card_type:"Warrior", card_name:"Zhang Fei", card_id:123},
               {card_type:"Mage", card_name:"Liu Bei", card_id:456}]
```

### 6.2 Sub-property Rules

- Each key is called a "sub-property" and has its own data type
- **Supports 5 basic types**: Text, Number, Datetime, Boolean, List
- **Nesting is not supported**: a sub-property cannot be of Object or Object Group type. If reported as either, it will be forcibly converted to "Text" or "List"

### 6.3 TE System Limits


| Limit Item | Upper Bound |
| ---------- | ------- |
| Number of objects in an object group | <= 500 |
| Number of sub-properties per object | <= 100 |


Exceeding this can be adjusted by contacting operations, but setting it too large is not recommended.

### 6.4 Reporting Format Requirements

- **Empty-value handling**: when an object/object group is empty, do not report the property (do not send an empty array `[]`), to avoid type anomalies caused by the first ingested record
- **Sub-property reporting**: in the actual reported JSON, sub-properties do **not carry the parent property name prefix**
  ```json
  ✅ Correct: {"fleet_info": [{"ship_id":"001", "ship_level":80}]}
  ❌ Wrong: {"fleet_info": [{"fleet_info.ship_id":"001"}]}
  ```
- **Distinguish Key and Value**: data with peer structures is reported via object groups; ID-type data (hero ID, card ID) must be Values, not Keys
  ```json
  ✅ Correct: [{"card_id":"123", "card_level":10}, {"card_id":"456", "card_level":20}]
  ❌ Wrong: {"123": {"level":10}, "456": {"level":20}}  // IDs cannot be Keys
  ```

### 6.5 Writing Rules in the Tracking Plan

In the tracking-plan Excel, object groups are written as:

1. **Parent property row**: property name is `xxx_info`, type is `Object Group`, and a JSON value sample is given in the property description
2. **Child property row**: property name is `xxx_info.child_name` (dot-separated), type is the actual sub-property type; leave the event name/display name/description/tag columns empty
3. A value sample must be provided:
  ```
   Value sample: [{"ship_id":"001","ship_level":80,"ship_power":5000}]
  ```

### 6.6 When to Use an Object Group (all three conditions met)


| Condition | Description |
| ---------- | ------------------------------ |
| A group of same-kind entities | An event needs to record multiple same-kind objects (e.g. multiple warships deployed, multiple items obtained) |
| Each entity has >= 2 properties | Each object needs to record 2 or more properties (otherwise a list suffices) |
| Variable count | The number of entities varies by scenario (when fixed at 1, use a plain property) |


### 6.7 Common Object Group Patterns


| Object Group Name | Scenario | Typical Sub-properties |
| ---------------------------------------- | --------- | -------------------------------------- |
| `hero_info` / `ship_info` / `fleet_info` | Battle lineup, character detail | id, level, star, power, equipment_list |
| `get_item_info` | Items gained detail | item_id, item_num |
| `cost_info` | Items consumed detail | item_id, item_num |
| `rank_info` | Leaderboard info | id, rank, score |
| `bag_info` | Inventory snapshot | item_id, item_num |

## 10. Property Enum Values & Dimension Table Management

### 10.1 TE Dimension Table Capability

The TE system supports **dimension tables** for managing and maintaining enum values:

- Storage location: `hive.ta_dim.dim_<Project ID>_<0|1>_`
- Creation path: Data Management > Asset Center > Cross-source Asset Configuration
- Enum value sources:
  - **Fixed enum**: configured via CSV file upload; displayed directly as analysis-module drop-down options
  - **Dynamic enum**: the system auto-queries property values and caches them to support analysis-model drop-down selection
- Dimension tables can be linked to event properties and user properties to implement ID -> name mapping

### 10.2 Enum Value Strategy in the Tracking Plan

**Principle: the tracking plan only defines the reporting format of properties; the display and management of enum values are delegated to dimension tables.**

#### Scenarios to enumerate in the tracking plan (for development alignment only)

1. The property value directly affects the reporting logic, and developers need to know the enums (e.g. `battle_type`, `token_type`)
2. The value range is fixed and small (<= 10), writable in one line
3. Label format: briefly list in the property description column
  ```
   Values: main / event / daily
  ```

#### Scenarios recommended for dimension-table management

1. Many enum values (> 10), e.g. item ID to item name, stage ID to stage name
2. Enum values that change frequently across version iterations (e.g. activity ID, product ID)
3. Analysis scenarios needing ID -> display-name mapping (e.g. `ship_id` -> ship name + rarity + faction)
4. Mark in the property description: `"Recommend dimension-table management; fields: xxx_id, xxx_name, xxx_type"`

#### Scenarios needing neither enumeration nor a dimension table

- Free text (`nick_name`, `fail_reason`)
- System auto-increment IDs (sequence numbers with no business meaning)
