# AE Automation

Create recurring Agent work as a platform automation through `ae-cli automation`. If any prerequisite or write command returns `error.type: auth` or `error.type: config`, or reports a permission denial or unsupported configuration, report the blocker and stop the automation workflow. Leave credential and environment diagnosis or repair to a separate user request. Do not substitute session-local `CronCreate`, `/loop`, or `scheduled_tasks.json` for the requested platform automation.

See [command risks](references/command_index.md). Read [the command contract](references/cli.md) before writing or executing an automation. Use `ae-cli automation --help` and leaf help to discover flags.

1. Resolve the host and space. A local user signs in with `ae-cli auth login`; a sandbox uses the current conversation user's injected CLI token, never a shared sandbox's user binding. Pass `--agent-space-id` when the user identifies a space. Without an explicit space, the CLI inherits the current AgentSpace from its runtime context, working directory or verified current conversation; only a local invocation without space context uses the personal default. Show the resolved space when it matters.
2. Discover the automation with `automation list` and inspect `automation get`. Use the returned IDs; names are not unique.
3. For creation, select an Agent or team through the corresponding discovery commands. Match configuration to the target type. Use `--weekdays` or `--days-of-month` JSON arrays for multiple days with one time; skip dates absent in a month. For the actual last day of every month use `--days-of-month '["L"]'`, or combine it with dates, e.g. `'[1,15,"L"]'`; overlapping selections execute only once. Both Agent and Agent Team accept result notifications. Save only the recurring task instructions as `--message`.
   - In a conversation, run `ae-cli automation create --dry-run` for each new task, including a second task in the same chat or one that will start paused. Show the name, space, target, task instructions, schedule, model and depth, notifications, conversation mode and initial state, including any immediate run. Ask the user to confirm this preview and wait for their reply. Use AskUserQuestion when available. Selecting a target or answering a clarification only completes the preview. A changed configuration needs a new preview and confirmation. A cancellation ends that draft. Only an explicit reply approving this task authorizes one creation.
   - For a single Agent, include reasoning depth in the confirmation. If no depth was requested, use adaptive without asking or copying the current conversation's setting. For an explicit depth, pass `--effort low|medium|high|max`. If the request is ambiguous or conflicting, clarify before creating.
   - In a shared workspace, select an enabled company Team. A personal Team is only a valid target in a personal workspace; do not silently switch workspace or Team. For an Agent Team, ignore any requested depth, even an unrecognized one. Use the team's own settings and continue without asking about depth. For a request to change only Team depth, use the CLI update with the supplied effort to verify permission. A successful `unchanged: true` means the override was ignored and the team still uses its own settings. With a mixed update, report the fields that were saved and the ignored depth separately.
4. Execute the requested operation. After creation, read back the returned automation ID with `automation get` and verify the saved space and configuration, including the Agent effort (`null` means adaptive) before reporting success. Link to the returned `detailPath` including its `agentSpaceId` query. A local schedule or a promise to run later is not a platform creation receipt. Deleting an automation or stopping an execution requires confirmation; use `--yes` only when the user already authorized that action. In a non-interactive shell, these operations fail immediately unless global `--yes` is present.
5. Read the returned run ID, then `automation runs result`. Report acceptance separately from completion. Use `--wait` only when the user needs the final outcome now.

Results are read from the server and work outside the sandbox. This skill does not read complete conversations or continue a chat. Never infer an output from a different execution sharing the same conversation.
