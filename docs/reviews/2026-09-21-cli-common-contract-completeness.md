## 一、为什么之前不断补契约

对 liaodesheng 的历史修改逐项回看后，问题集中在同一个功能跨越多个独立入口，某一入口支持不代表整个链路支持。例如：

- `699725e3a3` 已补递归筛选编译，但入口 schema 和严格解析仍把组合节点当作必须含字段／操作符的叶节点；CLI 送到编译器之前就被拒绝。
- `3e440dee88` 等时间功能已在原生 QP 存在，保存报表回读却不能还原动态周／月／季度／年和完整周期选项，更新时会改变窗口。
- `1e6b2e4537`、`a194ff6f` 已补异步导出，另外四个治理导出仍是普通命令，缺等待、下载、超时和本地文件处理。
- 排行、收入等原生功能已经实现，语义 DTO／编译器／回读映射仍只覆盖简化子集。CLI 接受一个 definition，不等于 Common 能完整编译或保留页面上建立的报表。
- `ca62a1d3`、`d0d28905`、`9bbd9c97` 等提交也体现同类问题：部分更新、动态日期、时区单位必须由 CLI 参数、服务契约和具体消费代码共同约束。

因此本次按 **CLI 实际发送 → capability schema → 严格 definition 解析 → 元数据解析 → 原生 QP 编译／消费 → report.get → update → 再编译** 检查。对可改变结果的字段增加往返验证，避免仅验证“创建成功”。

## 三、覆盖范围与明确边界

- 捕获344个已注册 CLI capability 命令的实际顶层输入，并与后端注册 schema 比较：344/344 捕获，未知字段0，缺失必填字段0。这是传输形状验证，**不等于344次真实业务执行**。
- 后端 schema 测试覆盖366个 capability 定义；不要求每个 capability 都有专用 CLI 命令。已按仓库准入规则保留 L3 `capability search/inspect/run` 入口，避免重复造命令。
- 12个 ad-hoc 模型（event、retention、funnel、interval、distribution、path、attribution、revenue、rank_list、heat_map、prop_analysis、sql）及保存标签、人群定义纳入检查。不同模型只暴露原生确实消费的选项。
- 热力图支持“对比组”，原生引擎没有日期对比消费逻辑，未伪造日期对比支持。
- 事件／属性分析根 `analysis_entity` 用于下钻；事件计数身份由各指标 `quota_entities` 决定，属性指标保持原生用户语义。没有把根实体错误宣称为所有模型指标的统一计数开关。
- 排行日期对比最多1个；留存每种同时指标角色最多1个；间隔窗口仅分钟／小时／天；历史标签仅按天。原生限制现在明确拒绝，而不再接受后静默改写。
- SQL 原生文本保持不变；不以自动改写 SQL 来伪装契约完整。纯显示信息与影响结果的分析选项分别评估。
