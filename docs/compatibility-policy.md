# CLI / Gateway 与已发布 Skill 兼容性规范

适用于命令、参数、Capability Gateway 契约及随正式版本发布的 Skill。开发和集成分支自动 review 都必须检查；版本检测和自动升级只能缩短版本错配窗口，不能代替兼容层。

## 一、公开契约

变更前对照已发布版本和本次 diff 基线，逐项识别以下契约；发布历史不明确时查证，不能把“不知道是否被使用”当作未发布：

- 命令路径、别名、参数名、类型、枚举、必填性、默认值及实际行为。
- Gateway capability ID、输入字段、输出结构、错误码、退出码、同步/异步及分页语义。
- 权限、公司/项目隔离、风险等级和确认流程；兼容不得放宽授权边界。
- Skill 名称、目录、职责、依赖和 reference 路径；已有安装、脚本、定时任务及 Agent 可能固定使用这些入口。

删除或重命名入口、可选参数改必填、缩小枚举、改变默认行为、输出类型或错误语义，都应按潜在不兼容变更评估。同一维护版本线默认保留既有契约；统一升级提示、客户端 schema 校验和新版本用例通过，均不能证明旧调用兼容。

## 二、命令与参数演进

1. 优先采用新增可选能力、保留旧别名、边界层转换或弃用提示。保留旧参数的解析和服务端接收，明确它映射到什么行为；不能只保留 CLI flag、同时从 Gateway schema 删除对应字段。
2. 参数已无实际作用时，可保留为 deprecated 兼容参数并清楚说明其行为，前提是不会改变安全、数据口径或产生额外写操作。只处理明确已知的旧字段，继续拒绝其他未知字段；不能用忽略所有未知输入替代兼容层。
3. 行为变化不能靠静默忽略掩盖。涉及数据口径、缓存、新写操作、权限或确认语义时，先明确兼容策略和用户可见说明；高风险操作的权限与确认保持有效。
4. 确需打破兼容时，先取得明确批准并记录受影响调用、迁移路径、支持窗口、版本与发布顺序、回滚方式；通过新版本入口或协调迁移完成，不在补丁版本直接移除旧契约。修改服务端时，评估旧 CLI/Skill/脚本仍在运行的情况。

例如 `analysis dashboard-report-data export --use-cache true`：导出不读取缓存，并不意味着可以直接删除已发布的 `use_cache` 输入。需要明确保留兼容输入及弃用说明，或使用获准的版本化迁移方案。缩短版本检测周期本身不会修复已经安装的旧 CLI 或固定脚本。

## 三、已发布 Skill 演进

- 已发布到正式版本库或发行包的 Skill 保留名称、入口及原有职责；不要直接删除、改名，或用同名 Skill 替换成另一项功能。
- 正常迭代在原 Skill 上更新内容并递增版本，同步维护依赖和 reference。合并职责时保留原入口及明确的兼容指引，避免已有安装和调用突然失效。
- 正式下线需要明确批准、受影响用户与依赖清单、弃用窗口、迁移和回滚方案；窗口内保留可用入口。未发布的内部 Skill 清理需提供未发布证据，且不能顺带删除正式入口。
- 控制 Skill 数量：新增前先检查已有职责能否覆盖；优先扩展或复用已有 Skill。确需新增时说明独立职责及无法复用的原因，避免一项接口一个 Skill、重复入口和职责碎片化。

## 四、验证与集成 review

完成或合并前必须给出兼容性结论及证据：

1. 对照修改前后的命令、flag、Gateway schema 和 Skill/reference，枚举移除、重命名、类型/默认值/语义变化；既有自动化脚本和固定版本客户端属于调用方。
2. 用旧命令和旧请求字段复测新实现，并验证新增行为。跨仓契约至少覆盖旧 CLI → 新服务端、新 CLI → 发布窗口仍支持的服务端；无法验证的组合如实列出，不能标记通过。
3. 验证弃用提示不会污染 JSON stdout，结构化错误和退出码仍可被脚本识别；权限、隔离、确认、导出生命周期和失败残留保持约定。
4. 对 Skill 变更检查已发布状态、入口和 reference 可达性、职责连续性、版本递增、数量与复用理由。
5. Review 优先报告无兼容层的公开契约移除及已发布 Skill 直接删除/替换，并给出具体旧调用、失败路径和改动位置；没有证据时列出验证缺口，不编造故障。

当前集成 review 是观察模式，报告不等于通过验证或批准合并；作者和人工 reviewer 仍需处理兼容性问题。新增检查要求不改变现有 CI 触发、通知及合并门禁行为。
